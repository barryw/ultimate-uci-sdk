# A generic sprite multiplexer, and the Boing demo on it

Date: 2026-09-02. Bench: Ultimate 64 Elite at 192.168.1.62, firmware 3.15,
core 1.4F, NTSC. Origin: `experiments/boing/`, whose ball is sixteen sprites a
frame out of eight, with three hand-written raster interrupts that know the
ball's shape. Depends on the four fixes in
`2026-09-02-sdk-fixes-from-boing-design.md`.

## Why

The Boing demo's multiplexer is the interesting part of the demo and the part
nobody else can use: it is written for two columns of four rows. The SDK
should offer the general thing, so that a program declares up to 32 sprites,
moves them, and gets them drawn out of the VIC's eight, and the demo should
be a thin consumer of that service.

This is the first module in the SDK that has nothing to do with the Ultimate:
it runs on a stock C64. It goes in because the SDK's demos need it and the
user asked for it. It uses no UCI, REU, turbo or audio call.

## Names

Amiga names, on purpose. A *VSprite* is a hardware sprite virtualised by
multiplexing, which is exactly this. A *bob* is a blitter object, which is
what `demos/vsprites` draws; that demo is misnamed by the same rule and is
not renamed here.

Module: `src/vic/vsprite.s`, listed in `src/uci/sources.mk` so the library,
the blob and the cc65 wrappers pick it up the same way as every other module.
Public names carry the SDK prefix: `ultimate_vsprite_init`,
`ultimate_vsprite_update`, `ultimate_vsprite_irq`.

## Caller-owned data

The SDK's RAM is 191 bytes today (`UCI_VARS_SIZE`). Two plan buffers need
about 500. So the caller supplies a work buffer, exactly as it supplies the
sprite table; the SDK keeps only a pointer to it and a handful of bytes.

### The record, 8 bytes, up to 32 of them

| Offset | Field | Meaning |
|---|---|---|
| +0 | `x` low | horizontal position, bits 0-7 |
| +1 | `x` high | bit 0 is the ninth bit, as `$D010`; other bits ignored |
| +2 | `y` | vertical position, as `$D001` |
| +3 | `pointer` | sprite data pointer, the byte the VIC reads at `sprptr + n` |
| +4 | `colour` | 0-15 |
| +5 | `flags` | bit 0 x-expand, bit 1 y-expand, bit 2 multicolour, bit 3 behind the background, bit 7 hidden |
| +6 | user | never read or written by the SDK |
| +7 | user | never read or written by the SDK |

Flag bits 4-6 are reserved and must be zero. A hidden record takes no
hardware slot and no step.

### The config

| Field | Size | Meaning |
|---|---|---|
| `table` | 2 | address of the first record |
| `count` | 1 | records in the table, 1-32 |
| `work` | 2 | address of `VSPRITE_WORK_SIZE` bytes the SDK owns from `init` on |
| `sprptr` | 2 | address of the eight sprite pointer bytes, screen + `$3F8` |
| `top` | 1 | raster line of the frame-start step |

`top` must be greater than every sprite's last line plus the gap, so that
step 0 lands after the last sprite of the frame and before the first of the
next; 250 on NTSC and PAL alike leaves room. The config is read once by `init` and
may be discarded.

### Constants

Generated by `tools/gen_protocol.py` into every binding, so C, ca65,
KickAssembler and ACME see the same numbers:

```
VSPRITE_MAX        = 32
VSPRITE_RECORD     = 8
VSPRITE_WORK_SIZE  = the exact work buffer size the layout below needs
VSPRITE_GAP        = 3     raster lines of margin around a slot change
VSPRITE_F_XEXPAND  = $01
VSPRITE_F_YEXPAND  = $02
VSPRITE_F_MCOLOR   = $04
VSPRITE_F_BEHIND   = $08
VSPRITE_F_HIDDEN   = $80
```

`VSPRITE_WORK_SIZE` is computed from the layout, never typed by hand.

## The three calls

### `ultimate_vsprite_init(config) -> result`

`A`/`X` = config address. cc65: `uint8_t ultimate_vsprite_init(const
ultimate_vsprite_config *cfg)`. Blob: the config is `bp_vsprite`, a new
field in the parameter block.

Validates: config, `table` and `work` non-null; `count` in 1-32; `top` not
zero (it is one byte, so at most 255 by construction). Anything else returns
`ULTIMATE_ERR_INVALID_ARGUMENT` and changes nothing. On success: copies the config into SDK RAM, clears the work buffer,
sets `order[]` to identity, marks no plan ready, marks the module up, returns
`ULTIMATE_OK`.

From here on `$D000-$D010`, `$D015`, `$D017`, `$D01B-$D01D`, `$D027-$D02E`
and the eight bytes at `sprptr` belong to the SDK. The caller sets the VIC
bank and screen before `init` and does not move them after.

### `ultimate_vsprite_update() -> dropped`

Main loop, once per frame after the caller has moved its records. Returns the
number of records that could not be given a hardware slot this frame. Before
`init` it returns 0 and does nothing.

### `ultimate_vsprite_irq() -> next line`

Called from the caller's raster interrupt handler, whatever vector that
handler hangs on. Applies one step of the active plan and returns the raster
line the caller should arm next. Returns `top` after the frame's last step;
the caller treats `A == top` as end of frame and does its per-frame work
(physics, then `update`). Never touches `$D012`, `$D011`, `$D019` or any
vector. Before `init` it returns 0 and writes nothing.

The caller's handler, at its simplest:

```
irq:    pha : txa : pha : tya : pha
        jsr ultimate_vsprite_irq
        sta $D012
        cmp #TOP
        bne done
        jsr per_frame           ; physics, then ultimate_vsprite_update
done:   asl $D019
        pla : tay : pla : tax : pla
        rti
```

## Inside `update`

1. **Sort.** Insertion sort of `order[]`, 32 bytes of record indices, by the
   record's `y`; hidden records sort after everything. Between frames the
   order is nearly right, so the sort is close to linear: 32 records in well
   under 3,000 cycles at 1 MHz.
2. **Slots.** `free[8]`, the first raster line each hardware sprite may be
   reprogrammed on, starts at 0. Walk `order[]`. For each visible record take
   the slot with the smallest `free`. If that `free` is greater than the
   record's `y - VSPRITE_GAP`, no line remains on which the slot could be
   reprogrammed in time, so the record is dropped this frame and counted;
   otherwise the slot is assigned and its `free` becomes `y + 21` (or
   `y + 42` when y-expanded) `+ VSPRITE_GAP`. Priority therefore follows `y`, then table
   order, and a record hides its partner only when more than eight overlap.
3. **Steps.** The first eight assignments are step 0, applied at `top`. Every
   later assignment has a window from its slot's previous `free` to its own
   `y - VSPRITE_GAP`. Greedily: if the current step's line lies in the window,
   join it; otherwise open a new step at the window's start. At most 31 steps
   after step 0; an assignment that would need a 32nd is dropped and counted.
4. **Snapshot.** Each plan entry copies slot, `x` low, `x` bit 8, `y`,
   pointer, colour and flags from the record. The interrupt reads only the
   plan, never the caller's table, so a record written half-way when the
   interrupt lands cannot tear a sprite.
5. **Publish.** The plan is built in the inactive buffer. `ready` is cleared
   before the first write and set after the last, a single byte store each,
   so the interrupt can never adopt a half-built plan. If `update` runs twice
   in a frame the second build wins.

### Work buffer layout

```
order      32            record indices, sorted by y
plan A     2 + 224 + 64  header (step count, $D015 mask for step 0),
                         32 entries of 7 (slot, x, xh, y, ptr, colour, flags),
                         32 steps of 2 (line, entry count)
plan B     290           the same
```

`VSPRITE_WORK_SIZE` is the sum, 612, computed in `gen_protocol.py` from
these sizes rather than typed. SDK RAM (not the work buffer) holds the config copy, `active`,
`ready`, `step`, `dropped` and the module-up flag.

## Inside `irq`

- **Step 0.** If `ready`: swap active and inactive, clear `ready`. Write
  `$D015` from the plan header: the slots step 0 uses, every other slot off,
  so a slot first used later in the frame cannot show stale data before its
  step. Program step 0's entries. If not ready, the same plan is applied
  again and the sprites hold still.
- **Later steps.** Program the step's entries; each entry also sets its
  slot's bit in `$D015`, which is a no-op for a slot step 0 enabled.
- **Per entry** (about 60 cycles at 1 MHz): `$D000 + 2n`, `$D001 + 2n`, bit
  `n` of `$D010`, `$D017`, `$D01D`, `$D01C`, `$D01B` (read-modify-write, safe
  because only this routine writes them once `init` has run), `$D027 + n`,
  `sprptr + n`.
- **Return** the next step's line, or `top` after the last. Eight entries
  take about eight raster lines at 1 MHz, which is why `VSPRITE_GAP` exists;
  it is one constant, tuned in VICE, and the documented knob to raise when a
  slow handler or a stock machine shows a torn sprite.

## Errors and edges

- `init`: null config, null `table` or `work`, `count` 0 or over 32, `top`
  0: `ULTIMATE_ERR_INVALID_ARGUMENT`. Reserved flag bits in a record are
  ignored at `update`, not rejected.
- `update` or `irq` before a successful `init`: no-ops, returning 0.
- More than eight sprites in one 21-line band: the ninth and later are
  dropped for that frame, counted, and the rest draw. Nothing flickers
  "automatically"; a caller that wants round-robin flicker rotates its
  table order.
- Raster lines are 8-bit. Sprite `y` is 8-bit in hardware, so no step ever
  needs a line above 255.
- Not done: sprite-over-sprite priority beyond `y` order, per-sprite
  callbacks, `$D011` bit 7 lines, detection of the VIC bank or screen.

## Bindings

- **ca65**: exports above; `bindings/asm/ultimate.inc` documents them.
- **cc65**: `ultimate_vsprite` and `ultimate_vsprite_config` structs in
  `include/ultimate.h` matching the offsets; wrappers in
  `bindings/cc65/ultimate_cc65.s` (`init` takes a pointer, the other two take
  nothing and return a byte); `abi_assert.c` checks the struct sizes against
  `VSPRITE_RECORD` and the config size.
- **Blob**: three entries appended to the jump table (`vsprite_init` reading
  `bp_vsprite`, `ultimate_vsprite_update`, `ultimate_vsprite_irq`), `bp_vsprite`
  appended to the parameter block, README rows, `test_blob_table.py` green.
  Because A3 is done first, the demo sees them as `uci.BLOB_VSPRITE_INIT`,
  `uci.BLOB_ULTIMATE_VSPRITE_UPDATE`, `uci.BLOB_ULTIMATE_VSPRITE_IRQ` and
  `uci.BLOB_BP_VSPRITE`.
- **Protocol constants**: the `VSPRITE_*` group in `gen_protocol.py`, so
  `docs/generated/protocol-constants.md` documents them too.

## The Boing demo on it

`experiments/boing` moves to `demos/boing` (the whole directory, `.gitignore`
included, so the Amiga sample stays out of git). Then:

- The ball is sixteen records: eight positions, each a white record and a red
  record at the same `x`/`y` with different pointers and colours, x-expanded,
  hires. Row `r` has `y = ball_y + 21 * r`; column `c` has
  `x = ball_x + 48 * c`. `build_set` and the two live sprite sets stay; the
  records' pointers change with the set.
- The three raster interrupts (`irq_vbl`, `not_vbl`, `irq_row3`) become the
  handler shown above. Physics, `build_set`, the shadow and the sound trigger
  run on `A == top`, exactly where the vblank work runs today.
- `audio_settle` and the init `AUDIO_STOP` go (A1). The `cmp #0`s go (A2).
  The `.const` offsets become `uci.BLOB_*` (A3).
- The sample leaves the PRG (A4). At init, after the REU is known to be
  there, the demo calls `audio_load_wav` with `boing.wav`, then with
  `/Temp/boing.wav`, into REU `$4000`; the first success sets the audio flag,
  and a failure leaves the demo silent with the result in the status block,
  exactly as a missing REU does today. `PCM`, `PCM2`, `boing_pcm.inc`, the
  two `reu_stash` calls and the KERNAL bank switch go. The PRG loses 17 KB
  but stays above the runner's 16 KB, so `hwtest.py` keeps its FTP path and
  uploads `boing.wav` beside the PRG.
- `mkpcm.py` becomes `mkwav.py`: same inputs (a WAV, or a raw signed 8-bit
  file and a rate, or nothing for the synthesised fallback), one output,
  `boing.wav`, 16-bit mono at the source rate. `make` builds it; `SAMPLE=`
  selects the input as now. The shipped sound is the synthesised fallback:
  the original recording is Amiga Corp's, stays git-ignored, and the README
  tells an owner of the Workbench Demos disk how to extract and pass it.
  Improving the synthesis is its own later task.
- VICE has no UCI, so the load fails there and the demo runs silent, as it
  does today; `make check` asserts flags 2 as before.
- The blob build is unchanged (`BASE=8000 VARS=43008`); the work buffer is
  the demo's, `VSPRITE_WORK_SIZE` bytes at `$5900`, after the clean screen
  copy (which ends at `$58E7`) and well before the bitmap at `$6000`.
- Memory map (`$aa00-$b911` and the `$e000` piece freed, work buffer at
  `$5900`), README ("What the SDK does here": turbo, REU, WAV load, audio,
  vsprite, one paragraph each), `NOTES.md` trimmed to what is still true.
- Top-level `Makefile`: `boing` and `boing-run` targets beside `vsprites`,
  not in `demos` (KickAssembler, like vsprites). `make -C demos/boing check`
  keeps the five-screenshot VICE check; `hwtest.py` unchanged.

## The cc65 example

`examples/cc65/vsprites.c`, about 80 lines: 32 sprites, one shape, bouncing
off the edges at different speeds, y-expanded on every fourth, the KERNAL
interrupt kept and the raster interrupt chained in front of it. It exists to
prove the C path compiles and runs, so it is small and has one VICE
screenshot check in its Makefile (`make -C examples/cc65 check-vsprites`).

## Tests

- **Emulator** (`tests/emulator/vsprite.suite`, run in both harness builds):
  a harness routine fills a table and config from suite-poked memory, calls
  `init`, `update` and `irq`, and stores each return value. Cases: identity
  order for sorted input; a reversed table sorts; nine sprites in one band
  drop one; two rows of four at `y` and `y + 21` reuse slots and produce a
  second step at `y + 21 + gap` (the Boing shape); `irq` step 0 writes the
  expected `$D000-$D010`, `$D015`, `$D017`, `$D01D` and pointer bytes and
  returns the second step's line; the last step returns `top`; `update`
  before `init` returns 0. Planning verifies that sim6502 treats `$D000-$D02E`
  as RAM; if it does not, the register assertions are replaced by assertions
  on the plan buffer.
- **VICE**: `demos/boing` `make check` (whole ball every screenshot, no
  shadow trail, bounce counted) and the example's screenshot.
- **Hardware**: `make boing-run U64_HOST=192.168.1.62` uploads the PRG and
  `boing.wav`, reports 60 fps, flags 7, bounces climbing with sound; three
  fresh launches clean.
