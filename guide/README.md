# The Ultimate SDK Programmer's Reference Guide

A compact guide to the SDK's BASIC, C, assembly and standalone
binary interfaces.

```
make            # -> guide.pdf
```

Needs cc65 plus a TeX installation with `tcolorbox`, `titlesec`, `avant` and
`inconsolata`. The build compiles the C and assembly call forms before it
creates the PDF.

## What is here

| | |
|---|---|
| `guide.tex` | covers, front matter, source checks, and chapter order |
| `ultimatesdk.sty` | page design, screens, listings, tables and keycaps |
| `chapters/` | one file per chapter |
| `examples/` | compile contracts for every documented C and assembly call form |

## Content rules

- State each technical fact once.
- Put a short explanation before or after every example naming the feature it
  demonstrates.
- Use `outputbox` only for literal text the C64 displays; use `resultbox` for
  return values, memory changes and descriptions of visible effects.
- Use `tip` only when the feature's role in a larger program is not obvious.
- Keep each technical section's source check in a non-printing
  `\evidence{...}` marker.
- Prefer generated contracts and executable tests to narrative documentation;
  the latter can become stale.

The covers and machine drawing are generated by TikZ, so the guide has no image
asset dependency.

## Writing a chapter

```latex
\guidechapter{TITLE IN CAPS}{%
  \item what this chapter covers
  \item one bullet per section
}

\section{A Section}
Body text.

\begin{screen}
PRINT UREU
\end{screen}
```

`screen` is for what you type at the machine; `listingbox` is for source you
keep in a file; `outputbox` is literal C64 text; `resultbox` describes a
non-text result. `\key{return}` draws a keycap; `note`, `tip`, and `warning`
are the callout environments.

## Verify a change

Build the PDF with `make -C guide`. Run `make unittest` for generated tables,
keyword dispatch, register boundaries and blob ABI checks; run `make test` when
an example or claim depends on assembled SDK behaviour.

Then run `make -C guide hardware U64_HOST=<address>` for the standalone C and
assembly examples, including the selective-linking and custom-workspace builds.
This checks screen RAM and border-register effects on the Ultimate; compiling
`c_calls.o` and `assembly_calls.o` checks call forms, not execution of every API.
Run the affected SDK/BASIC/demo hardware suites too, one at a time, as listed in
[the test guide](../tests/README.md#hardware-is-part-of-completion). Record
failures, missing fixtures, and any visual/audio checks still needing a person.
